# Atlassian MCP Server Constitution

## Назначение

Настоящая конституция определяет обязательные инженерные принципы, архитектурные
ограничения и правила разработки Atlassian MCP Server.

Все спецификации, технические планы и реализации MUST соответствовать положениям
настоящего документа.

Если конкретное требование задачи противоречит конституции, противоречие MUST быть
явно выявлено и согласовано до реализации.

## Core Principles

### I. Простота и отсутствие преждевременной универсальности

Архитектура должна решать существующие задачи, а не гипотетические потребности
будущих версий.

- MUST предпочитать простейшее решение, удовлетворяющее текущим требованиям.
- MUST NOT создавать абстракции, слои и механизмы расширения без конкретной
  необходимости.
- MUST NOT реализовывать функциональность, не предусмотренную требованиями.
- MUST NOT усложнять архитектуру ради потенциальной поддержки сценариев, которые
  пока не рассматриваются.
- SHOULD предпочитать композицию универсальным фреймворкам и избыточным иерархиям
  наследования.
- SHOULD отдавать предпочтение стандартным возможностям .NET перед созданием
  собственных инфраструктурных механизмов.

Любое существенное архитектурное усложнение MUST иметь обоснование конкретной
потребностью.

### II. Разделение ответственности

Компоненты приложения должны иметь чётко определённые обязанности и минимальную
связанность.

- MUST отделять обработку MCP-запросов от прикладной логики.
- MUST изолировать детали взаимодействия с REST API Jira и Confluence в
  инфраструктурном слое.
- MUST сохранять независимость Core от MCP SDK, Refit, HTTP и конкретных
  инфраструктурных реализаций.
- MUST NOT допускать зависимости Core от Infrastructure.
- MUST NOT раскрывать MCP-инструментам детали реализации HTTP-клиентов и Refit.
- MUST NOT смешивать описание HTTP-контрактов Atlassian с контрактами
  MCP-инструментов.
- SHOULD размещать функциональность в том компоненте, которому она соответствует
  по ответственности.

Разделение ответственности не должно приводить к созданию избыточных уровней
абстракции.

### III. Интеграция с Atlassian

Взаимодействие с Jira и Confluence должно осуществляться через официальные REST API
соответствующих продуктов.

- MUST использовать официальные REST API Jira и Confluence.
- MUST NOT использовать сторонние Atlassian SDK.
- MUST использовать Refit для декларативного описания HTTP API.
- MUST описывать вручную только те REST API endpoint, которые необходимы
  реализуемой функциональности.
- MUST учитывать различия REST API Jira и Confluence.
- MUST учитывать совместимость с целевыми версиями Jira Data Center 10.x и
  Confluence Data Center 8.x.
- MUST корректно учитывать context path в базовых URL серверов.
- MUST NOT переносить детали Atlassian REST API непосредственно в публичные
  контракты MCP-инструментов.

Модели HTTP-ответов должны описывать структуру внешнего API, а прикладные модели —
потребности приложения.

### IV. Ориентация на AI-агента

MCP Server является адаптером между Atlassian REST API и AI-агентом. Его интерфейс
должен быть ориентирован на задачи агента, а не на механическое отображение
внешнего API.

- MUST проектировать MCP-инструменты вокруг законченных и понятных операций.
- MUST использовать понятные и предсказуемые названия инструментов и параметров.
- MUST предоставлять структурированные и информативные результаты.
- MUST обеспечивать понятное представление ошибок.
- MUST ограничивать объём возвращаемых данных с учётом ограничений контекста LLM.
- MUST NOT предоставлять прямые аналоги REST endpoint в качестве MCP-инструментов
  без конкретной необходимости.
- SHOULD предусматривать разумные значения параметров по умолчанию.
- SHOULD минимизировать количество дополнительных вызовов, необходимых агенту для
  выполнения типовых задач.

Ответы MCP-инструментов должны содержать достаточно информации для принятия
агентом дальнейших решений, но не должны включать избыточные данные.

### V. Безопасность

Безопасность должна учитываться при проектировании каждого компонента,
взаимодействующего с внешними системами и обрабатывающего конфиденциальные данные.

- MUST использовать отдельные Personal Access Token для Jira и Confluence.
- MUST использовать PAT исключительно для соответствующей системы.
- MUST NOT передавать PAT MCP-клиентам или возвращать их через MCP-инструменты.
- MUST NOT записывать PAT, заголовки Authorization и другие секреты в логи.
- MUST передавать PAT через переменные окружения.
- MUST NOT передавать PAT через аргументы командной строки.
- MUST NOT отключать проверку TLS-сертификатов.
- MUST проверять корректность обязательной конфигурации при запуске приложения.
- MUST применять принцип минимально необходимых привилегий.
- MUST NOT раскрывать конфиденциальные данные в диагностических сообщениях и
  ответах об ошибках.

Для работы с серверами, использующими self-signed сертификаты, следует использовать
настройку доверенных сертификатов, а не отключать проверку TLS.

### VI. Надёжность и эффективное использование ресурсов

Приложение должно корректно взаимодействовать с внешними API, учитывать ограничения
удалённых систем и управлять ресурсами собственного процесса.

- MUST использовать асинхронное выполнение операций ввода-вывода.
- MUST поддерживать передачу CancellationToken через все уровни выполнения операций.
- MUST корректно обрабатывать ошибки HTTP-взаимодействия.
- MUST сохранять информацию о HTTP Status Code при преобразовании ошибок внешних
  API.
- MUST учитывать различия форматов ошибок Jira и Confluence.
- MUST поддерживать пагинацию при получении коллекций данных.
- MUST ограничивать объём загружаемых и возвращаемых данных.
- MUST корректно обрабатывать HTTP-ответы без тела, включая 204 No Content.
- MUST корректно формировать URL с учётом context path.
- MUST корректно обрабатывать завершение процесса и отмену выполняемых операций.

Обработка ошибок не должна приводить к потере существенной диагностической
информации или раскрытию конфиденциальных данных.

### VII. Целостность и гибкость моделей данных

Модели приложения должны учитывать особенности данных Atlassian, включая
динамические поля и пользовательские настройки.

- MUST учитывать наличие пользовательских полей Jira (custom fields).
- MUST NOT предполагать, что все возможные поля Jira заранее известны приложению.
- MUST NOT молча отбрасывать неизвестные поля, если они имеют значение для
  выполняемой операции.
- MUST сохранять необходимые метаданные при преобразовании внешних моделей.
- MUST использовать типизированные свойства для стабильных и часто используемых
  полей.
- SHOULD использовать гибкие JSON-представления для динамических и заранее
  неизвестных данных.
- SHOULD различать отсутствующие, пустые и null-значения, если это различие имеет
  значение для контракта внешнего API.

Не следует создавать избыточные статические модели, пытающиеся заранее описать все
возможные варианты данных Jira и Confluence.

### VIII. Тестируемость и итеративная разработка

Архитектура должна обеспечивать возможность проверки прикладной логики без
необходимости постоянного взаимодействия с реальными экземплярами Atlassian.

- MUST обеспечивать возможность независимого тестирования прикладной логики.
- MUST разделять модульные и интеграционные тесты.
- MUST NOT требовать доступ к реальным экземплярам Jira и Confluence для выполнения
  обычных модульных тестов.
- MUST покрывать автоматическими тестами критически важное поведение.
- MUST проверять корректность обработки ошибок и граничных условий.
- MUST NOT писать отдельные автоматизированные тесты, единственная цель которых —
  проверять передачу или срабатывание `CancellationToken`.
- MUST реализовывать функциональность итеративно.
- MUST реализовывать операции чтения до внедрения операций изменения данных.
- MUST проверять совместимость с поддерживаемыми версиями Jira и Confluence.

Исправление обнаруженных дефектов SHOULD сопровождаться регрессионными тестами,
если это практически возможно.

### IX. Совместимость контрактов

Изменение публичных контрактов должно учитывать существующих потребителей MCP
Server.

- SHOULD сохранять обратную совместимость существующих MCP-инструментов при
  расширении функциональности.
- MUST явно выявлять изменения, нарушающие обратную совместимость.
- MUST обосновывать необходимость breaking changes.
- MUST NOT изменять поведение существующих инструментов незаметно для их
  потребителей.

Изменения, нарушающие обратную совместимость, допускаются при наличии обоснованной
необходимости.

### X. Наблюдаемость и диагностика

Приложение должно предоставлять достаточную диагностическую информацию для
выявления и устранения проблем.

- MUST использовать стандартные механизмы логирования .NET.
- MUST направлять диагностические сообщения в stderr.
- MUST резервировать stdout исключительно для MCP-протокола при использовании STDIO.
- MUST обеспечивать возможность диагностики ошибок взаимодействия с Jira и
  Confluence.
- MUST NOT записывать секреты и конфиденциальные данные в логи.
- SHOULD использовать структурированное логирование.
- SHOULD включать в диагностические сообщения контекст операции, необходимый для
  поиска проблемы.

Дополнительные механизмы наблюдаемости должны внедряться только при наличии
конкретной потребности.

### XI. Правила работы с операциями изменения данных

Операции, изменяющие состояние Jira или Confluence, должны быть явно отделены от
операций чтения.

- MUST явно различать read-only и write-операции.
- MUST учитывать права пользователя, от имени которого выполняется операция.
- MUST предоставлять агенту понятное описание последствий операций изменения данных.
- MUST предусматривать дополнительные меры защиты для потенциально разрушительных
  операций.
- MUST NOT выполнять операции изменения данных, если их намерение и параметры не
  определены достаточно явно.

Добавление write-операций не должно приводить к ухудшению безопасности и
предсказуемости существующих read-only инструментов.

### XII. Язык и документация проекта

Основным языком коммуникации и проектной документации является русский.

- MUST использовать русский язык для общения с пользователем, спецификаций,
  технических планов и архитектурной документации.
- MUST использовать английский язык для имён и описаний MCP-инструментов и их
  параметров: это публичный контракт для AI-агента, а не проектная документация.
- MUST вести `README.md` на английском языке: это витрина проекта для внешних
  пользователей; остальная проектная документация остаётся русской.
- MUST сохранять оригинальные названия технологий, API, библиотек и технических
  идентификаторов.
- MUST NOT переводить имена классов, методов, интерфейсов, переменных и других
  программных идентификаторов.
- SHOULD использовать общепринятую английскую терминологию там, где перевод может
  сделать техническое описание менее однозначным.

## Governance

Настоящая конституция является нормативным документом проекта и должна учитываться
при подготовке спецификаций, технических планов и реализации функциональности.

- MUST проверять соответствие предлагаемых архитектурных решений применимым
  принципам конституции.
- MUST выявлять противоречия между требованиями и принципами до начала реализации.
- MUST обосновывать исключения из обязательных принципов.
- MUST обновлять конституцию при изменении фундаментальных инженерных решений
  проекта.
- MUST сопровождать изменения конституции обоснованием.
- MUST использовать семантическое версионирование конституции.

Порядок внесения поправок: изменение конституции предлагается с указанием
затрагиваемых принципов и обоснования, проверяется на соответствие действующим
обязательствам и фиксируется вместе с новой версией. Соблюдение конституции
проверяется при подготовке спецификаций, технических планов и в ходе код-ревью.

Версионирование:

- PATCH — уточнение формулировок без изменения смысла принципов.
- MINOR — добавление новых принципов или требований без изменения существующих
  обязательств.
- MAJOR — удаление принципов или изменение смысла существующих обязательств.

Конституция не должна дублировать спецификации функциональности, технические планы
и инструкции по реализации. Она определяет устойчивые правила, в рамках которых эти
документы создаются и реализуются.
