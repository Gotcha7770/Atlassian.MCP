# AGENTS.md

Правила для AI-агентов и разработчиков, работающих с этим репозиторием.
Нормативные инженерные принципы — в `.specify/memory/constitution.md`; здесь — конкретные
договорённости о написании кода, которые не являются принципами уровня конституции.

## Код-стиль

- Источник истины по форматированию и code style — `.editorconfig`. Если правило задано
  там (отступы, переносы, длина строки, кавычки и т. п.), следуй ему, а не своим
  предпочтениям; перед сдачей прогоняй Reformat Code (cleanup).
- Правила ниже применяются только там, где `.editorconfig` молчит.

## Тесты

Тестовый код пишется для читателя, а не для переиспользования: ясность, выразительность и
очевидность важнее DRY и оптимальности.

- Всё существенное — в теле теста: данные, действия, проверки. Читатель не должен ходить
  по хелперам, чтобы понять сценарий.
- Повтор между тестами допустим, если он делает тест самодостаточным. В общий метод
  выносится повторяющееся **нетривиальное** действие (инициализация, генерация данных),
  а не одна-две строки.
- Тест должен падать так, чтобы из сообщения было понятно, что сломалось: имя теста
  описывает поведение, проверка — один смысл.
- Если тест разросся или появилась общая подготовка:
  - **Bogus** — для генерации тестовых данных;
  - **xUnit fixtures** (`IClassFixture`/`ICollectionFixture`) — для общей инициализации;
  - не статические хелперы «на все случаи».
- Оптимизация в тестах (кэширование, экономия вызовов, переиспользование состояния) —
  не цель: предсказуемость и независимость тестов важнее.
- Ясность не означает копипаст ради копипаста: если повтор скрывает намерение или
  расходится между тестами, он выносится.
- В тестах передавай `TestContext.Current.CancellationToken`, а не `CancellationToken.None`:
  xUnit отменяет тест по своему таймауту, и токен должен доходить до кода.
- Тестовые данные создавай прямо в методе теста: должно быть видно, с каким объектом
  работает конкретная проверка.
- Выноси в общий метод только то, что реально переиспользуется в нескольких тестах.
  Хелпер ради одного вызова не создавай: он отдаляет данные от проверки и добавляет
  лишний переход по коду.
- Юнит-тесты на логирование не писать: ни уровень, ни текст сообщений не проверяем.
  Логи — диагностика для оператора; поведение проверяется по результату инструмента
  и по модели ошибки.
- Не писать тесты на поведение фреймворка и библиотек (сериализация `[]`/`null`
  в `System.Text.Json`, разбор JSON, регистрация в DI): тест проверяет наш код или
  зафиксированный контракт. Исключение — когда поведение задаётся нашей конфигурацией
  и её изменение сломает контракт.

## Задачи в tasks.md

- Задача описывает объект (файл или тип), действие, ожидаемый результат и способ проверки.
- Формулировки вида «передан в запрос» без указания запроса, поля и проверяемого результата
  не использовать.
- При запуске `speckit.implement` SpecKit управляет порядком выполнения и контрольными
  точками; статусы задач ведутся только в `specs/<feature>/tasks.md`.
- Не создавай второй список статусов задач или параллельный ledger в `.superpowers/`.
  Записи о решениях или проверках допустимы только без повторения статусов задач.
- Глобальное правило выбора workflow и его явных пользовательских переопределений
  задано в `C:\Users\Gleb\.config\opencode\AGENTS.md`.

## Файлы и типы

- Один top-level тип на файл, имя файла совпадает с именем типа (`AtlassianOptions.cs` →
  `AtlassianOptions`). Не собирай несколько классов, записей, интерфейсов или перечислений
  в одном файле.
- Вложенные `private` типы допустимы, если принадлежат объявлению внешнего типа —
  например, тестовые двойники внутри тестового класса.

## Записи (records)

- Свойства внутри записи пишутся подряд, без пустых строк между ними.
- Если у записи больше двух свойств или свойства имеют атрибуты (например,
  `[JsonPropertyName]`), не используй позиционный синтаксис — раскрывай полноценные
  свойства с `get; init;` (изменяемость — только если действительно нужна).
- `[JsonPropertyName]` не нужен, если сериализатор настроен на camelCase (Refit по
  умолчанию, `JsonSerializerOptions.Web`): размечай модель только при реальном
  расхождении имён.

## Конструкторы

- Primary конструкторы в классах и структурах не использовать (`class Foo(IDep dep)`):
  зависимости принимай явным конструктором и сохраняй в `private readonly` поле.
- В позиционных записях primary конструктор допустим, пока свойств не больше двух и ни у
  одного из них нет атрибутов. Иначе раскрывай запись свойствами с `get; init;`.

## Именование

- Имя типа не повторяет сегмент своего неймспейса: в
  `Atlassian.Mcp.Infrastructure.Jira.Models` — `Issue`, а не `JiraIssue`. Префикс
  оправдан, только если тип — граница системы и без него теряет смысл (`JiraClient`,
  `IJiraApi`, `JiraTools`, `JiraErrorParser`) либо различает соседние реализации в одном
  файле.
- Обратное правило: не убирай префикс, если без него имя становится слишком общим.
  `JiraUser` остаётся `JiraUser`, а не `User`: «пользователь» сам по себе не говорит, чей
  он и в каком слое, и такое переименование потом откатывают.
- Имена MCP-инструментов и их параметров — camelCase (`jiraGetIssue`, `issueKey`): это публичный контракт для агента.
- Имя метода начинается с глагола и описывает действие: `GetCurrentUser`, `SearchIssues`,
  `CheckAvailabilityAsync`. Существительное без глагола (`CurrentUser`, `Myself`) не
  использовать — по имени должно быть понятно, что метод делает.

## Методы

- Не создавай метод-обёртку ради одной строки или одного обращения — вызывай напрямую.
  Общий метод оправдан, если используется в нескольких местах и содержит собственную
  логику.

## Методы расширения

- Расширения объявляй extension-блоком C# 14 — `extension(ILogger logger) { ... }`, — а не
  параметром `this` (`this ILogger logger`).
- Класс расширений — статический, имя по шаблону `<Тип>Extensions` (`UrlExtensions`),
  файл называется так же.
- Исключение: расширения `IServiceCollection` — класс и файл `DependencyInjection`
  (`DependencyInjection.cs`); это сознательный выбор проекта.
- Члены extension-блока объявляй с явной доступностью (`public`, `internal`), не полагайся
  на доступность по умолчанию.
- Правило «не создавай метод ради одного обращения» из раздела «Методы» действует и здесь.

## Длина строки

- Лимит бери из `.editorconfig` (`max_line_length`) или `.idea/*.DotSettings`, если он
  там задан. Если не задан — 120 символов для всего проекта.
- Лимит соблюдай везде: объявления методов, атрибуты, аргументы вызовов, тесты.

## Форматирование вызовов

- Expression-bodied метод: если тело умещается в лимит строки — пиши в одну строку;
  если не умещается — обычный метод с фигурными скобками и `return`. Перенос
  expression-bodied метода на следующую строку не использовать.
- Не вкладывай вызов в аргумент другого вызова или конструктора
  (`new X(GetOptions(p).Value)`): вынеси результат в локальную переменную и передай её.
- Не читай свойства возвращаемого объекта в той же строке, где вызываешь метод
  (`GetRequiredService<IOptions<T>>().Value`): сначала сохрани результат, свойства —
  следующей строкой.
- Цепочку вызовов (fluent API, `Should()`, builder, LINQ-конвейер) оформляй построчно:
  каждый вызов — с новой строки.
- Исключение: если после `Should()` идёт ровно одна проверка и она умещается в строку,
  оставляй их в одной строке — `error.Value.Should().BeNull();`.

## Утверждения

- Все проверки — через AwesomeAssertions (`value.Should()...`), а не через `Assert.*`
  из xUnit: сообщения о сбое информативнее.
- Act и Assert не смешивай: результат действия сохраняй в переменную, проверку делай
  следующей строкой. Запись вида `Validate(options).Should()...` недопустима.
- Один элемент коллекции проверяй цепочкой
  `items.Should().ContainSingle().Which.Should().Satisfy<T>(item => { ... })`,
  внутри — утверждения по отдельным полям.
- Когда проверяется много полей одного объекта, сравнивай графы объектов через
  `.Should().BeEquivalentTo(...)`; ожидаемый объект создавай прямо в аргументе — это
  исключение из запрета вкладывать вызов в аргумент другого вызова.
- Исключения — `using static AwesomeAssertions.FluentActions;` и
  `await Awaiting(() => ...).Should().ThrowAsync<TException>().Where(e => ...)`;
  `.Where` вызывается прямо в цепочке (есть extension на `Task<ExceptionAssertions<T>>`).
  `Assert.ThrowsAsync` и `Func<Task> act` не использовать.
- В `Awaiting` — только целевая операция. Подготовка (создание провайдера, получение
  зависимостей) выполняется в Arrange, до `Awaiting`: иначе в проверяемое действие
  попадает лишний код и сбой указывает не на ту причину.

## Перед сдачей

- Прогони `dotnet build` и `dotnet test` и приведи результат в ответе. Утверждать, что
  всё работает, без вывода команд нельзя.
- Отступление от любого правила этого файла — только после явного вопроса пользователю.
  Не решай сам, что правило здесь не подходит, и не заменяй его своей оптимизацией.
- Если правила конфликтуют или мешают выполнить задачу — остановись и спроси, какое
  главнее; молча выбирать не нужно.
- Новое правило сразу применяй к существующему коду: найди нарушения в затронутой
  области и исправь их в том же изменении.
