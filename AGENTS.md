# AGENTS.md

Правила для AI-агентов и разработчиков, работающих с этим репозиторием.
Нормативные инженерные принципы — в `.specify/memory/constitution.md`; здесь — конкретные
договорённости о написании кода, которые не являются принципами уровня конституции.

## Код-стиль

- Источник истины по форматированию и code style — `.editorconfig`. Если правило задано
  там (отступы, переносы, длина строки, кавычки и т. п.), следуй ему, а не своим
  предпочтениям; перед сдачей прогоняй Reformat Code (cleanup).
- Правила ниже применяются только там, где `.editorconfig` молчит.

## Тесты

- В тестах передавай `TestContext.Current.CancellationToken`, а не `CancellationToken.None`:
  xUnit отменяет тест по своему таймауту, и токен должен доходить до кода.
- Тестовые данные создавай прямо в методе теста: должно быть видно, с каким объектом
  работает конкретная проверка.
- Выноси в общий метод только то, что реально переиспользуется в нескольких тестах.
  Хелпер ради одного вызова не создавай: он отдаляет данные от проверки и добавляет
  лишний переход по коду.

## Файлы и типы

- Один top-level тип на файл, имя файла совпадает с именем типа (`AtlassianOptions.cs` →
  `AtlassianOptions`). Не собирай несколько классов, записей, интерфейсов или перечислений
  в одном файле.
- Вложенные `private` типы допустимы, если принадлежат объявлению внешнего типа —
  например, тестовые двойники внутри тестового класса.

## Записи (records)

- Если у записи больше двух свойств или свойства имеют атрибуты (например,
  `[JsonPropertyName]`), не используй позиционный синтаксис — раскрывай полноценные
  свойства с `get; init;` (изменяемость — только если действительно нужна).
- `[JsonPropertyName]` не нужен, если сериализатор настроен на camelCase (Refit по
  умолчанию, `JsonSerializerOptions.Web`): размечай модель только при реальном
  расхождении имён.

## Именование

- Имя метода начинается с глагола и описывает действие: `GetCurrentUser`, `SearchIssues`,
  `CheckAvailabilityAsync`. Существительное без глагола (`CurrentUser`, `Myself`) не
  использовать — по имени должно быть понятно, что метод делает.

## Методы

- Не создавай метод-обёртку ради одной строки или одного обращения — вызывай напрямую.
  Общий метод оправдан, если используется в нескольких местах и содержит собственную
  логику.

## Длина строки

- Лимит бери из `.editorconfig` (`max_line_length`) или `.idea/*.DotSettings`, если он
  там задан. Если не задан — 120 символов для всего проекта.
- Лимит соблюдай везде: объявления методов, атрибуты, аргументы вызовов, тесты.

## Форматирование вызовов

- Expression-bodied метод: если тело умещается в лимит строки — пиши в одну строку;
  если не умещается — обычный метод с фигурными скобками и `return`. Перенос
  expression-bodied метода на следующую строку не использовать.
- Не вкладывай вызов в аргумент другого вызова или конструктора
  (`new X(GetOptions(p).Value)`): вынеси результат в локальную переменную и передай её.
- Не читай свойства возвращаемого объекта в той же строке, где вызываешь метод
  (`GetRequiredService<IOptions<T>>().Value`): сначала сохрани результат, свойства —
  следующей строкой.
- Цепочку вызовов (fluent API, `Should()`, builder, LINQ-конвейер) оформляй построчно:
  каждый вызов — с новой строки.
- Исключение: если после `Should()` идёт ровно одна проверка и она умещается в строку,
  оставляй их в одной строке — `error.Value.Should().BeNull();`.

## Утверждения

- Все проверки — через AwesomeAssertions (`value.Should()...`), а не через `Assert.*`
  из xUnit: сообщения о сбое информативнее.
- Act и Assert не смешивай: результат действия сохраняй в переменную, проверку делай
  следующей строкой. Запись вида `Validate(options).Should()...` недопустима.
- Один элемент коллекции проверяй цепочкой
  `items.Should().ContainSingle().Which.Should().Satisfy<T>(item => { ... })`,
  внутри — утверждения по отдельным полям.
- Исключения — `using static AwesomeAssertions.FluentActions;` и
  `await Awaiting(() => ...).Should().ThrowAsync<TException>().Where(e => ...)`;
  `.Where` вызывается прямо в цепочке (есть extension на `Task<ExceptionAssertions<T>>`).
  `Assert.ThrowsAsync` и `Func<Task> act` не использовать.
- В `Awaiting` — только целевая операция. Подготовка (создание провайдера, получение
  зависимостей) выполняется в Arrange, до `Awaiting`: иначе в проверяемое действие
  попадает лишний код и сбой указывает не на ту причину.
